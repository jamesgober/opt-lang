# opt-lang v0.3.0 — ir-lang alpha.3 and OPS v2

**One IR version for the native path.** opt-lang 0.2 pinned ir-lang
2.0.0-alpha.1 while irgen-lang 0.2 emits alpha.2, so the family's native path
(HIR → irgen-lang → ir-lang → opt-lang → backend-lang → machine code) could not
run end to end (ISSUES P37). v0.3.0 moves to ir-lang **2.0.0-alpha.3**,
optimizes the OPS v2 operations (`pow`, `shift = saturate`) in every pass, uses
the rewrite operations ir-lang added at opt-lang's request, and is tested on
programs built the way irgen-lang lowers: SSA variables and automatic
statepoints.

Still not connected: backend-lang 0.3 pins alpha.1 and irgen-lang 0.2 pins
alpha.2, so no front end feeds opt-lang 0.3 and no backend reads it yet. The
other halves of P37 are backend-lang 0.4 and irgen-lang 0.3 on alpha.3.

## What is opt-lang?

The IR-to-IR stage of the `-lang` family's native compiler path. It depends
on `ir-lang` (`=2.0.0-alpha.3`) and `pass-lang` (`1`), nothing else, and
rewrites `ir_lang::Module`s in place: sparse conditional constant
propagation, value numbering, dead-code elimination, CFG simplification, copy
propagation, and loop-invariant code motion, run to a fixpoint.

## What's new in 0.3.0

### OPS v2 in every pass

```rust
use ir_lang::{BinaryOp, BlockArg, BlockCall, InstData, Linkage, Module, Overflow, Policy, Signature, Type};

// fn f(x: i64) -> i64 { x ** 2 }  -- a signed pow is always a `check`
let mut m = Module::new("demo");
let f = m.declare_function("f", &Signature::new(&[Type::I64], &[Type::I64]), Linkage::Export)?;
let mut b = m.build(f)?;
let x = b.param(0)?;
let two = b.iconst(Type::I64, 2)?;
let ok = b.create_block(&[Type::I64])?;
let err = b.create_block(&[Type::U32])?;
b.check(
    InstData::Binary { op: BinaryOp::Pow, policy: Policy::overflow(Overflow::Trap), args: [x, two] },
    BlockCall::with_args(ok, &[BlockArg::Result(0)]),
    BlockCall::with_args(err, &[BlockArg::ErrorCode]),
)?;
b.switch_to(ok)?;
let sq = b.block_param(ok, 0)?;
b.ret(&[sq])?;
b.switch_to(err)?;
b.trap(6)?;

opt_lang::optimize(&mut m)?;
let text = m.display_function(f).to_string();
assert!(text.contains("mul<overflow=trap> v0, v0") && !text.contains("check"));
# Ok::<(), Box<dyn std::error::Error>>(())
```

- **Folding.** Integer `pow` is folded exactly (overflow per policy; a negative
  exponent is `NegativeExponent`, code 6, under every policy, `trap` included,
  as alpha.3 and OPS section 6 define it). Float `pow` is folded with
  ir-lang's `ls_pow`, the routine every tier shares, so the folded bits are
  the run-time bits (a NaN result is left to run time). `saturate` shifts fold
  to `0` or the sign fill. Everything is checked against the interpreter's
  `eval_binary` on every type and policy.
- **Partial folding.** With one operand known: `x ** 0` and `x * 0` are
  constants, `x ** 1` and `x + 0` are `x`, a negative constant exponent always
  raises, `1 ** y` is `1` whenever it succeeds, and the error kinds that remain
  are tracked, so a `check` knows which of its edges can be taken and which
  code its error edge carries. Each rule is property-tested against the
  interpreter.
- **`check` rewrites that ir-lang accepts.** ir-lang alpha.3 decides
  plain-versus-`check` with `can_error(policy, type)`: a signed `pow` is
  always fallible. opt-lang makes a `check` plain only when that rule accepts
  the plain form; `x ** 2` becomes `x * x` under the same overflow policy;
  signed `saturate` shifts by known non-negative amounts become `mask` shifts;
  and a `check` that must stay but cannot raise (say `x ** 3` under `wrap`)
  keeps its `check` with the dead error edge sent to a shared `unreachable`
  block, so the error handler can be deleted. An error edge that can be taken
  is never touched.

### The rewrite operations ir-lang added for opt-lang

`Builder::move_inst` (O(1)) replaces the 0.2 move-by-copy-and-forward, and
`Builder::remove_block_params` (one linear pass) replaces the 0.2 block
rebuilds. Measured with criterion against 0.2's code on the same ir-lang and
machine (the spread across runs on this machine is about ±10%):

| Benchmark | Change |
|---|---:|
| `edit/simplify-cfg-merge` (merging a 50,000-block chain: 200,000 moves) | −32% to −53% (two runs) |
| `pass/simplify-cfg` (100k / 1M instructions) | −23% / −23% |
| `pass/licm` (100k / 1M) | −18% to −28% |
| `pipeline/optimize` (100k / 1M), against 0.2.0's published run | ~69 ms → ~43 ms / ~1.12 s → ~0.89 s |
| `edit/dce-dead-params` (DCE removing 350,000 parameters) | no change to −16% (two runs) |
| `pass/dce`, `pass/copy-prop` | within noise |

Moves gained most: the old path inserted a copy, forwarded every result, and
tombstoned the original. Parameter removal was already linear in 0.2 (the
rebuild path); the gain there is modest, blocks keep their handles, and the
rebuild code is gone.

### Statepoints

No pass moves a call or `safepoint`, edits a GC list, or makes a `ref` (or a
value derived from one) constant, value-numbered, or hoisted, so input whose
statepoints came from `Builder::insert_statepoints` stays valid without
re-running it. The tests hold this two ways: the validator after every pass,
and `insert_statepoints` run on every optimized GC and variable-API program,
which must find nothing to add.

## Verification

- Differential (interpreter before vs after; pipeline, each pass, random
  sequences) with the generator now emitting `pow` (constant and variable
  exponents) and `saturate` shifts, each placed in a `check` exactly when
  `can_error` requires.
- New `tests/variables.rs`: random programs built with `declare_var`,
  `def_var`, `use_var`, `seal_block`, signed `check pow`/`saturate`, and a GC
  reference across calls with statepoints from `insert_statepoints`; pipeline
  and every pass alone, validated and run.
- Per-pass OPS v2 tests on textual IR; hostile `check pow` chains and 10,000
  `pow`s by `u64::MAX`; `error_kinds` equal to `can_error` for every operation,
  policy, and type.

## Known limitations

- **ir-lang alpha.3's validator is quadratic** on a deep chain of blocks whose
  error edges all join one handler (debug build: 5,000 `check`s 0.3 s, 20,000
  6.7 s), and every optimizer run validates its input. opt-lang's passes are
  linear on that shape. Reported for the ISSUES ledger; the hostile tests use
  5,000-long chains.
- **irgen-lang is not a dev-dependency**: irgen-lang 0.2 pins
  `=2.0.0-alpha.2`, which cannot coexist with `=2.0.0-alpha.3` in one Cargo
  graph. `tests/variables.rs` builds the same kind of input directly.
- Strength reduction is limited to `x ** 2`; memory optimizations, inlining,
  SROA, and `fma` folding remain planned for 0.5.0.
